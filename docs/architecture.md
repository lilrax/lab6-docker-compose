# Архитектура лабораторной работы №5

## 1. Общая идея

Проект реализует микросервисную архитектуру на Python.

Приложение разделено на два независимо запускаемых сервиса:

- **API Gateway** — принимает HTTP-запросы от пользователя, проверяет данные и обращается к Storage Service.
- **Storage Service** — выполняет операции с товарами и сохраняет информацию в базе SQLite.

Сервисы взаимодействуют по HTTP, используя REST API и JSON.

## 2. Схема взаимодействия

```text
                  Пользователь
                       |
                       | HTTP / JSON
                       v
              +------------------+
              |   API Gateway    |
              | 127.0.0.1:8000   |
              +------------------+
                       |
                       | HTTP / httpx
                       v
              +------------------+
              | Storage Service  |
              | 127.0.0.1:8001   |
              +------------------+
                       |
                       | SQL
                       v
              +------------------+
              |  SQLite Database |
              |   data/items.db  |
              +------------------+
```

Gateway не работает с SQLite напрямую. Доступ к базе данных осуществляется только через Storage Service.

## 3. Как проходит запрос

Рассмотрим создание товара.

1. Пользователь отправляет `POST /items` на API Gateway по порту `8000`.
2. FastAPI принимает запрос, а Pydantic проверяет входные данные.
3. Gateway передаёт запрос в доменный сервис `ItemService`.
4. `ItemService` обращается к репозиторию `HttpItemRepository`.
5. Репозиторий с помощью библиотеки `httpx` отправляет HTTP-запрос в Storage Service на порт `8001`.
6. Storage Service проверяет данные и вызывает свой `ItemService`.
7. SQLite-репозиторий сохраняет товар в базе данных.
8. Storage возвращает созданный товар с уникальным ID.
9. Gateway получает ответ, преобразует данные в типизированную модель и возвращает результат пользователю.

При успешном создании товара пользователь получает код `201 Created`.

При получении существующего товара через `GET /items/{item_id}` возвращается `200 OK`.

## 4. Слои приложения

Оба микросервиса используют разделение на логические слои.

### API

Файлы `app/api/routes.py` и `app/api/schemas.py`.

Отвечают за HTTP-эндпоинты, обработку запросов, проверку входных данных и формирование ответов.

### Domain

Файлы `app/domain/models.py`, `ports.py` и `services.py`.

Содержат модели предметной области, бизнес-правила и контракты взаимодействия с хранилищем.

Здесь проверяются, например, правила создания товара: название не должно быть пустым, цена должна быть положительной, количество не должно быть отрицательным.

### Storage

В Storage Service файл `app/storage/repository.py` отвечает за SQL-запросы к SQLite.

В API Gateway файл `app/storage/client.py` реализует обращение к другому микросервису через HTTP.

Таким образом, одинаковое понятие «репозиторий» имеет разные реализации.

## 5. Protocol и Dependency Injection

В проекте используется `typing.Protocol` для описания интерфейса репозитория.

Доменный сервис знает, что репозиторий должен уметь создавать и получать товары, но не зависит от конкретного способа хранения.

**Dependency Injection** означает передачу готовой зависимости в сервис извне.

Например, в рабочем приложении можно передать SQLite-репозиторий или HTTP-репозиторий, а в тестах — тестовую реализацию в памяти.

Благодаря этому бизнес-логику можно тестировать независимо от базы данных и сети.

## 6. Конфигурация

Каждый микросервис имеет собственные настройки в файле `.env`.

Конфигурация загружается с помощью `pydantic-settings`.

Для Storage задаются адрес, порт, путь к базе SQLite и уровень логирования.

Для Gateway задаются адрес, порт, URL Storage, таймаут HTTP-запросов и уровень логирования.

Файлы `.env.example` служат примерами конфигурации.

## 7. Обработка ошибок

| Код | Ситуация |
|---|---|
| `200 OK` | Товар успешно найден |
| `201 Created` | Товар успешно создан |
| `404 Not Found` | Товар с указанным ID отсутствует |
| `422 Unprocessable Entity` | Переданы некорректные данные |
| `502 Bad Gateway` | Storage вернул некорректный ответ |
| `503 Service Unavailable` | Storage недоступен или возникла ошибка соединения |

Gateway обрабатывает исключения и преобразует их в понятные HTTP-ответы.

Если Storage остановлен, Gateway продолжает принимать запросы, но возвращает `503` для операций, которым нужен Storage.

При восстановлении Storage запросы снова могут выполняться успешно.

## 8. Тестирование

Тесты организованы отдельно для каждого микросервиса.

**Storage Service:**
- Проверка бизнес-логики.
- Проверка FastAPI-эндпоинтов.
- Проверка валидации данных.
- Проверка сохранения информации в SQLite.
- Использование временной тестовой базы данных.

**API Gateway:**
- Проверка бизнес-логики.
- Проверка HTTP-эндпоинтов.
- Проверка ошибок `404`, `422` и `503`.
- Проверка HTTP-клиента через `httpx.MockTransport`.
- Проверка сетевых ошибок, таймаутов и некорректных ответов.

По результатам тестирования:

| Сервис | Пройдено тестов | Покрытие кода |
|---|---:|---:|
| Storage Service | 18 | 99% |
| API Gateway | 28 | 95% |
| **Всего** | **46** | — |

## 9. Преимущества архитектуры

Разделение на микросервисы позволяет независимо запускать компоненты, изолировать ответственность за данные и внешний API, тестировать отдельные слои и управлять ошибками взаимодействия.

При этом архитектура становится сложнее монолитного приложения: появляются сетевые запросы, таймауты, необходимость запуска нескольких процессов и обработки недоступности одного из сервисов.

## 10. Заключение

В лабораторной работе реализована система из двух Python-микросервисов, взаимодействующих через REST API.

Проект демонстрирует использование FastAPI, Pydantic, httpx, SQLite, Protocol, Dependency Injection, обработки ошибок и автоматического тестирования.

Основная идея работы — разделить бизнес-логику, транспортный уровень и хранение данных, сохранив возможность независимого тестирования компонентов.
